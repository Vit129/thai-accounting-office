# thai-accounting-office

Claude Desktop (Cowork) plugin: a boss-loop workflow (the user decides, Claude runs the job, an independent auditor checks) plus Thai accounting skills for an accounting office. Every skill reads its lessons and the office memory before a job, writes a job ledger entry after it, and learns from corrections.

- Layout: `.claude-plugin/plugin.json`, `skills/*/SKILL.md` (English, Thai triggers), `agents/` (doc-reader=haiku, auditor=opus/fable), `hooks/hooks.json` (prompt Stop hook), `CONNECTORS.md` (~~email, ~~spreadsheet, ~~cloud storage). Model routing: Small/daily=haiku, Medium/periodic=sonnet (+opus review), Large/annual=opus.
- Runtime data lives in the user's work folder `Accountant/`, never in this repo: lessons `Accountant/lessons/<skill>.md` (how to do a job, no company data), the permanent memory `Accountant/memory/` (`accountant-memory`: decisions, party treatments, recurring entries, period balances, sources, formulas, and a job ledger of every job with its files/sheet/range, email subjects, formulas, checks and problems). Promote lessons into SKILL.md monthly, bump the skill version and the plugin version at release.
- `accountant-graph` is the light graph over the office's documents: `catalog.tsv` (one line per document or email read) and `links.tsv` (job/document/party/formula/period edges) in `Accountant/memory/`, plain TSV searched with file tools (no program, so it works in Claude Desktop). Search first before every job (`accountant-chief`, `accountant-memory` look-up), then live in the folder and mailbox; `document-intake` and `inbox-triage` register what they read. Keys are names, document numbers, forms, accounts and periods (the accounting counterpart of class/function names); `aka:` in `parties.md` joins spellings. The map artifact is untested in Claude Desktop.
- The engine is `skills/accountant-graph/scripts/` (`graph.py` search, ledger, queries, map, lessons and promote; `mcp_server.py` exposes it as `accountant_*` tools via the root `.mcp.json`; `stop_gate.py` is the command Stop hook that blocks once when a reported job has no ledger entry). Standard library only; each piece fails open without Python and the skills fall back to the manual steps. Tests: `python3 -m unittest discover -s tests -v` (run by `build.sh`; `tests/` is not shipped). `build.sh` excludes only the repo-root `scripts/`, never the skill's. Keep tool names in skills equal to `mcp_server.TOOLS` (a test checks it). Opening this repo in Claude Code also reads the root `.mcp.json` as a project server, where `${CLAUDE_PLUGIN_ROOT}` is not set, so that server shows as failed (CONNECTION_CLOSED) during development; ignore it or deny it for this folder. Untested in Claude Desktop: MCP start, `${CLAUDE_PLUGIN_ROOT}` expansion, the command hook, Windows `python3`.
- Every `skills/*/SKILL.md`, all of them including `learn-and-improve` and `accountant-memory` (which also hold the mechanism), ends with the same `## Learn and remember (every job)` block: lessons and memory before, ledger and lesson after. Add the block to any new skill; the Stop hook (`hooks/hooks.json`) blocks once when a job ended without a ledger entry (`บันทึกงาน J-...`) or a correction without a lesson.
- Windows: Claude Desktop on Windows runs the same plugin (skills/agents/prompt hook need no shell). Build there with `scripts/build.ps1` (untested on a real Windows box as of 2026-10-15); `.gitattributes` keeps .ps1 CRLF and .sh LF.
- Validate: `claude plugin validate .claude-plugin/plugin.json`, then package with `bash scripts/build.sh [company]` (writes `.plugin` + `.zip` to `dist/`). `claude plugin validate` is looser than Claude Desktop's uploader (Customize > Plugins > Add > Upload plugin): the uploader rejects `<` or `>` in a SKILL.md description, so build.sh fails on them. Agents' `<example>` blocks passed the uploader (2026-10-16).
- Never put client data in this repo.
- One base plugin for everyone (decided 2026-10-19; the single `thai-accounting-office` build is what gets installed). Company-specific facts are data in the user's work folder (`Accountant/company-facts.md`), asked at setup by `company-profile`; no per-company build is shipped. `companies/_template/` stays for the day a company needs rules the base cannot express (build with `bash scripts/build.sh <slug>`); the base `company-profile` is then replaced by that layer's file. First in-house user: a technology company's accountant (JD 2026-10-16); base skills still say "client" and `company-profile` Mode (in-house / firm) maps it.
- Adapting on site (once the friend reports back): facts and tax-rate overrides (`## Tax rate overrides`) go to the user's `Accountant/company-facts.md`, no rebuild. Skill rates are sourced defaults. The folder's state (New / Setup unfinished / Plugin updated / Working) is decided by `company-profile` step 0; bump `Template version` in `skills/company-profile/references/work-folder-CLAUDE.md` whenever that file changes. A rebuild is needed only for skill/hook changes; review `tune-up-week-<n>.md` reports, fix generic gaps in `skills/`, then `bash scripts/build.sh`, send the `.zip`; the user removes the old plugin and uploads the new one (guide: https://claude.ai/code/artifact/f3e4ea12-2365-4807-b6f9-64cb6e3065d7).
- Handoff for the company-side Claude: `skills/company-profile/references/handoff.md` (ships in the plugin; read at first-time setup) + `work-folder-CLAUDE.md` (copied to the user's work folder as `CLAUDE.md`). Update the handoff whenever the data rules or the company-tune-up loop change. `คู่มือการใช้งาน.html` at the repo root (not shipped; build.sh excludes `*.html`) is the beginner guide with the work-folder `CLAUDE.md` embedded (download/copy buttons). When `work-folder-CLAUDE.md` changes, re-embed it in the html (the escaped text in `<pre id="md">`); build.sh fails if the `Template version` line differs.
